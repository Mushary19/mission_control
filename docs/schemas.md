Generated by [`scripts/gen_schemas.py`](../scripts/gen_schemas.py); do not edit by hand. For each pipeline step: what it reads, the file it writes, the fields, one real example (long lists cut to 2 items) and the rules that apply. Field tables come from the Pydantic models in [`backend/app/schemas/`](../backend/app/schemas/) where one exists. Small readable samples of every file are in [`out/samples/`](../out/samples/) ([`scripts/make_samples.py`](../scripts/make_samples.py)).

**Conventions.** `*_local` times are Sri Lanka time (UTC+05:30), `*_utc` times are UTC. Keys that are null or empty are left out of the `.jsonl` files. Message `text` is cut to 200 characters; `GET /api/events/{id}/raw` returns the full original line(s). Every `.json` file except `pipeline_report.json` has a `step` key naming the step that wrote it.

## ID conventions

| id | format | example |
|---|---|---|
| `event_id` | `<source>:<native id>`: mail `internetMessageId`, calendar `iCalUId`, Teams chat `chatId:messageId`, Teams channel message id | `teams_channel:1772439208663` |
| screen `event_id` | `screen:<mailbox>:<line of the first frame>` | `screen:hana:3` |
| `person_id` | `p_<first>-<last>`; a personal-address record kept apart gets `-personal` | `p_chiara-ekwueme`, `p_luca-bellweather-personal` |
| `org_id` | `o_<short name>` | `o_fennimore` |
| `case_id` | leave: `leave:<person>:<first day>_<last day>`; offboarding and onboarding: `<process>:<person>` (one case per person) | `leave:amara-jaramillo:2026-03-23_2026-03-23`, `onboarding:chiara-ekwueme` |
| `flag_id` | `<rule>:<case_id>`, or `<rule>:<process>` for process-level rules | `laptop_requested_late:onboarding:chiara-ekwueme`, `sick_leave_two_ways:leave` |
| insight `id` | patterns: `ins:<process>:<name>`; case flags: `flag:<flag_id>` | `ins:onboarding:laptop_late` |
| open question `id` | `<process>-q<n>` | `leave-q1` |
| feedback `id` | 12 hex characters, random | `6cadb282fb65` |

## Step 1 · Ingest

**Reads** mail, calendar, Teams chat, Teams channel and screen logs from `data/`. **Writes** [`out/1_events.jsonl`](../out/1_events.jsonl) ([sample](../out/samples/1_events.sample.json)): one event per mail, calendar or Teams record. Screen sessions are built here but written in step 2.

| field | type | required | meaning |
|---|---|---|---|
| `event_id` | `string` | yes | "&lt;source>:&lt;native id>"; screen sessions use "screen:&lt;mailbox>:&lt;first line>" |
| `source` | `one of ['mail', 'calendar', 'teams_chat', 'teams_channel', 'screen']` | yes | `mail`, `calendar`, `teams_chat`, `teams_channel` or `screen` |
| `mailbox` | `string` | yes | the exported mailbox the record came from |
| `seen_in` | `list[string]` | no | mailboxes that had a copy |
| `time_utc` | `string` | yes | UTC |
| `time_local` | `string` | yes | Asia/Colombo (UTC+05:30) |
| `actor_id` | `string` | no | person id of who did it |
| `recipients` | `list[string]` | no | person ids it was sent to |
| `title` | `string` | no | subject, meeting title or window title |
| `text` | `string` | no | Plain text, cut to 200 chars; the full record is served by /api/events/{id}/raw |
| `text_truncated` | `bool` | no | `text` was cut |
| `category` | `one of ['process', 'context', 'noise', 'out_of_scope']` | no | `process`, `context`, `noise` or `out_of_scope` |
| `noise_reason` | `string` | no | why it is noise or out of scope |
| `activity` | `string` | no | activity id, e.g. `it_ready` |
| `process` | `one of ['leave', 'offboarding', 'onboarding']` | no | `leave`, `offboarding` or `onboarding` |
| `subject_person_id` | `string` | no | person the record is about |
| `resolution` | `Resolution` | no | how `subject_person_id` was found |
| `fields` | `object` | no | values extracted by the rule (dates, client, needed-by, `rule_id`) |
| `thread_key` | `string` | no | conversation key used to join replies |
| `raw_ref` | `RawRef` | yes | file + line of the original record |
| `session` | `Session` | no | screen session details (screen events only) |
| `meta` | `object` | no | source-specific extras (chat members, raw line numbers of screen frames) |

Example (Tobias's Teams message, before cleaning):

```json
{
  "actor_id": "p_tobias-northcott",
  "event_id": "teams_chat:19:f28c105d-3926-4a17-aa09-f29d953f48f1_6bf46c69-0a09-4f64-aab1-c3ba13deef86@unq.gbl.spaces:1773025571882",
  "mailbox": "hana",
  "meta": {
    "chat_members": [
      "p_hana-pemberton",
      "p_tobias-northcott"
    ]
  },
  "raw_ref": {
    "file": "data/hana/teams/messages.jsonl",
    "line": 23
  },
  "recipients": [
    "p_hana-pemberton"
  ],
  "seen_in": [
    "hana"
  ],
  "source": "teams_chat",
  "text": "all set for Chiara",
  "thread_key": "chat:19:f28c105d-3926-4a17-aa09-f29d953f48f1_6bf46c69-0a09-4f64-aab1-c3ba13deef86@unq.gbl.spaces",
  "time_local": "2026-03-09T08:36:11+05:30",
  "time_utc": "2026-03-09T03:06:11Z"
}
```

Rules:

* Every time is converted to Sri Lanka time and UTC, whatever the source format (UTC `Z`, `+05:30`, or a naive time with a Windows time-zone name).
* The same item seen in several mailboxes becomes one event (mail by `internetMessageId`, calendar by `iCalUId`, Teams by chat + message id); `seen_in` lists the mailboxes.
* Screen frames of the same window (same mailbox and title, short gaps) become one session.
* `raw_ref` (file + 1-based line) always points back to the original line.

## Step 2 · Clean

**Reads** the step 1 events and screen sessions. **Writes** three files:

### `2_events_clean.jsonl` ([sample](../out/samples/2_events_clean.sample.json))

The step 1 event plus its label: `category`, `process`, `activity`, `subject_person_id`, `resolution` and extracted `fields` (`rule_id`, dates, client, needed-by date). Same fields as the Event table above. Inside it:

Resolution (how the person the event is about was found):

| field | type | required | meaning |
|---|---|---|---|
| `method` | `string` | yes | email / sender / chat_member / thread / full_name / initial / first_name_unique / fuzzy / context / chat_pair / ambiguous / unresolved |
| `confidence` | `one of ['high', 'medium', 'low']` | no | `high`, `medium` or `low` |
| `reason` | `string` | no | Plain sentence: why this person was chosen |
| `raw_name` | `string` | no | the name as written |
| `candidates` | `list[string]` | no | person ids that fit the name |

Session (screen events only):

| field | type | required | meaning |
|---|---|---|---|
| `start_local` | `string` | yes | first frame, local time |
| `end_local` | `string` | yes | last frame, local time |
| `start_utc` | `string` | yes | first frame, UTC |
| `end_utc` | `string` | yes | last frame, UTC |
| `frame_count` | `int` | yes | screen frames in the session |
| `minutes` | `float` | yes | session length |

  "process": "onboarding",

  },
  "fields": {
    "linked_event_id": "teams_chat:19:f28c105d-3926-4a17-aa09-f29d953f48f1_6bf46c69-0a09-4f64-aab1-c3ba13deef86@unq.gbl.spaces:1772779280227",

Example screen session:

```json
{
  "event_id": "screen:lerato:7",
  "source": "screen",
  "title": "Leave tracker 2026.xlsx - Excel",
  "category": "context",
  "activity": "tracker_updated",
  "session": {
    "end_local": "2026-03-02T10:01:53+05:30",
    "end_utc": "2026-03-02T04:31:53Z",
    "frame_count": 2,
    "minutes": 9.9,
    "start_local": "2026-03-02T09:51:56+05:30",
    "start_utc": "2026-03-02T04:21:56Z"
  }
}
```

Rules:

* `category`: `process` (a step of leave, offboarding or onboarding), `context` (related but not a step), `noise` (small talk, newsletters, lock screen), `out_of_scope` (recruitment, birthdays, laptop replacements, payroll). Nothing is deleted; `noise_reason` says why.
* Activities come from one rule table (`pipeline/rules.py`); `fields.rule_id` names the rule that fired.
* Screens are read by window title and address, never by the app name.
* Names are resolved in this order: email, sender, chat member, thread, full name, first name + initial, unique first name, typo (fuzzy), case context. Every match stores a plain `reason`. When more than one person fits, `method` is `ambiguous` and `candidates` lists them; nothing is guessed.

### `2_people.json` ([sample](../out/samples/2_people.sample.json))

`people[]`, `orgs[]` and `identity_merges[]`.

| field | type | required | meaning |
|---|---|---|---|
| `person_id` | `string` | yes | person id (see ID conventions) |
| `display_name` | `string` | yes | name shown in the UI |
| `emails` | `list[string]` | no | every address seen for this person |
| `kind` | `one of ['staff', 'it', 'worker', 'new_starter', 'client', 'vendor', 'candidate', 'unknown']` | yes | `staff`, `it`, `worker`, `new_starter`, `client`, `vendor`, `candidate`, `unknown` |
| `org` | `string` | no | org id |
| `org_name` | `string` | no | organisation name |
| `exported` | `bool` | no | their mailbox is in the export |
| `job_title` | `string` | no | from the staff directory |
| `merged_ids` | `list[string]` | no | person ids merged into this one |
| `merge_reason` | `string` | no | why records were merged |
| `possible_same_person` | `list[PossibleSame]` | no | records that may be the same person, with a reason |

Example (a person with a possible duplicate):

```json
{
  "display_name": "Jun Hargreaves",
  "emails": [
    "jun.hargreaves@harbourline.example"
  ],
  "exported": false,
  "kind": "worker",
  "org": "o_harbourline",
  "person_id": "p_jun-hargreaves",
  "possible_same_person": [
    {
      "person_id": "p_jun-hargreaves-personal",
      "reason": "work address has no onboarding events; client not known on both sides"
    }
  ],
  "teams_ids": []
}
```

Rules: a personal and a work address are merged only with onboarding evidence (personal address used first, work address later, same client); `merge_reason` says why. Otherwise both records stay and `possible_same_person` asks staff "Is this the same person?".

Context, noise and out-of-scope screen sessions, too many to list one by one, summarised as table rows.

| field | type | meaning |

| `category` | `string` | context · noise · out_of_scope |
| `title` | `string` | window title |
| `sessions` | `int` | sessions of that title that day |
| `frames` | `int` | screen frames |

`rows` are arrays in `columns` order; `reason_by_title` gives the label reason per title; `totals` sums sessions and frames per category.

## Step 3 · Cases

**Reads** clean events and people. **Writes** [`out/3_cases.json`](../out/3_cases.json) ([sample](../out/samples/3_cases.sample.json)): `cases[]`, plus `person_last_days[]` (each leaver's last day, for cross-process checks) and `unlinked_process_events[]`.

| field | type | meaning |
|---|---|---|
| `case_id` | `string` | see ID conventions |
| `process` | `string` | `leave`, `offboarding`, `onboarding` |
| `subject_person_id · subject_name` | `string` | who the case is about |
| `client` | `string` | `org_id` of the client, if any |
| `owner_staff_id` | `string` | People team member who handled it |
| `staff_involved` | `string[]` | person ids of staff who did steps |
| `handoff` | `bool` | more than one staff member did the steps |
| `key` | `object` | what identifies the case: leave `dates` and `leave_type`, `last_day`, `first_day` |
| `status` | `string` | outcome: `complete`, `in_progress`, `declined`, `cancelled` |
| `started_before_window · ends_after_window` | `bool` | window badges: steps likely before 2 Mar · after 29 Mar |
| `window_notes` | `string[]` | why a badge was set |
| `start · end · last_activity` | `string` | local times of the first and last step |
| `steps` | `CaseStep[]` | the case's steps in time order (table below) |
| `flags` | `string[]` | `flag_id`s from step 5 |
| `out_of_order` | `object[]` | pairs of steps in an unexpected order |
| `summary` | `string` | one-line plain-English summary |

Case step:

| field | type | required | meaning |
|---|---|---|---|
| `activity` | `string` | yes | activity id, e.g. `it_ready` |
| `label` | `string` | yes | readable activity name |
| `event_id` | `string` | yes | event id (see ID conventions) |
| `time_local` | `string` | yes | Sri Lanka time (UTC+05:30) |
| `actor_id` | `string` | no | person id of who did it |
| `actor_name` | `string` | no | display name of who did it |
| `source` | `one of ['mail', 'calendar', 'teams_chat', 'teams_channel', 'screen']` | yes | `mail`, `calendar`, `teams_chat`, `teams_channel` or `screen` |
| `confidence` | `one of ['high', 'medium', 'low']` | yes | `high`, `medium` or `low` |
| `likely` | `bool` | yes | True for screen-based steps: the screen shows what was open, not what was done |
| `link` | `string` | yes | How the step joined the case: thread / dates / person / time |
| `link_reason` | `string` | yes | plain sentence: why the step joined this case |
| `raw_ref` | `RawRef` | yes | file + line of the original record |
| `session` | `Session` | no | screen session details (screen events only) |
| `title` | `string` | no | subject, meeting title or window title |

Rules:

* Leave cases are keyed by person and dates; offboarding and onboarding have one case per person. A step joins by thread first, then dates, then person, then time (`link`, with a `link_reason`).
* **Confidence** of a step: `high` = an explicit message names the action and the person, or it is in the same thread; `medium` = a calendar entry, or the person was matched by a short name, typo or case context; `low` = seen on screen or linked by time only.
* **Likely**: every screen-based step has `likely: true` and is shown as "Likely": a screen shows what was open, not what was done.
* **Status vs window badges**: `status` is only the outcome. Whether steps fall outside 2–29 March is shown separately by `started_before_window` and `ends_after_window`, never as missing steps.

## Step 4 · Discover

**Reads** cases. **Writes** [`out/4_processes.json`](../out/4_processes.json) ([sample](../out/samples/4_processes.sample.json)): `processes[]`, one model per process. The same model is served by `GET /api/processes/{process}`.

| field | type | meaning |
|---|---|---|
| `process` | `string` | `leave`, `offboarding`, `onboarding` |
| `case_count` | `int` | cases of this process |
| `full_trace_cases` | `int` | complete cases that start inside the window: what the main path rests on |
| `status_counts · window_badges` | `object` | cases per status · per badge |
| `main_path` | `MainPath` | the usual order of steps |
| `steps` | `ProcessStep[]` | every activity seen, with support and timing |
| `dfg` | `DfgEdge[]` | directly-follows graph: how often step A is followed by step B |
| `variants` | `Variant[]` | distinct step sequences and their cases |
| `open_questions` | `OpenQuestion[]` | questions for staff where the data is thin |
| `path_confidence` | `PathConfidence` | high · medium · low, with the reason and the rule |
| `insight_ids · process_flags` | `string[]` | links to step 5 and 6 |

MainPath:

| field | type | required | meaning |
|---|---|---|---|
| `activities` | `list[string]` | yes | activity ids in order |
| `labels` | `list[string]` | yes | readable names of the main path |
| `method` | `string` | yes | how the main path was chosen |
| `cases_following_exactly` | `int` | yes | complete in-window cases whose steps match the main path exactly |
| `tied_alternatives` | `list[object]` | no | other variants with the same support |

ProcessStep:

| field | type | required | meaning |
|---|---|---|---|
| `activity` | `string` | yes | activity id, e.g. `it_ready` |
| `label` | `string` | yes | readable activity name |
| `support_pct` | `float` | yes | % of the process's cases containing the step |
| `case_count` | `int` | yes | cases containing it |
| `confidence_mix` | `dict[string, int]` | yes | steps per confidence level |
| `on_main_path` | `bool` | yes | the step is on the main path |
| `optional` | `bool` | yes | under 50% support or off the main path |
| `median_from_case_start_h` | `float` | no | median hours from case start to this step |
| `median_to_next_h` | `float` | no | median hours to the next main-path step |
| `next_on_main_path` | `string` | no | the following main-path activity |
| `screen_only` | `bool` | yes | seen only on screens |

Variant:

| field | type | required | meaning |
|---|---|---|---|
| `path` | `list[string]` | yes | activity ids in order |
| `count` | `int` | yes | cases with this exact sequence |
| `case_ids` | `list[string]` | yes | cases following this variant |

| field | type | required | meaning |
|---|---|---|---|

| field | type | required | meaning |
|---|---|---|---|
| `id` | `string` | yes | id (see ID conventions) |
| `process` | `one of ['leave', 'offboarding', 'onboarding']` | yes | `leave`, `offboarding` or `onboarding` |
| `question` | `string` | yes | the question for staff |
| `why` | `string` | yes | what in the data raised it |
| `evidence` | `object` | no | the numbers behind the question |

PathConfidence:

| field | type | required | meaning |
|---|---|---|---|
| `level` | `one of ['high', 'medium', 'low']` | yes | `high`, `medium` or `low` |
| `reason` | `string` | yes | plain-English reason |

## Feedback (runtime)

**Written by** `POST /api/feedback` to SQLite (`backend/feedback.db`) and appended to `out/feedback.jsonl` (git-ignored). `GET /api/feedback/export` downloads all rows as JSONL.

Request (`FeedbackIn`):

| field | type | required | meaning |
|---|---|---|---|
| `user` | `string` | yes | Who is reviewing (no auth; picked in the UI) |
| `target` | `one of ['process_step', 'case_step', 'case', 'open_question', 'insight', 'identity']` | yes | what the feedback is about |
| `verdict` | `one of ['confirm', 'reject', 'add', 'answer']` | yes | `confirm`, `reject`, `add` or `answer` |
| `process` | `one of ['leave', 'offboarding', 'onboarding']` | no | `leave`, `offboarding` or `onboarding` |
